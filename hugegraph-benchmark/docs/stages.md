## 阶段 1 的完成条件

1. 发布对象有明确版本、任务语义、规模档、输入文件与校验和，能够独立于 CLI 使用。
2. 每道题具备固定参数及参考答案或可接受答案规则；漏结果、错结果、超时、缺项不能得到有效成绩。
3. 正式性能 profile 固定环境披露、缓存、预热、负载、测量、重复、计时与验证边界。
4. 固定成绩卡、有效性与比较规则；任何综合指标都必须公开基线、权重和失败处理。
5. 用最小适配器完成真实查询验证、A/A、已知退化、驱动容量校准，并由另一环境/使用者复现。
6. 准备可审阅的版本化发布候选与证据；公开发布遵循仓库评审/发布流程。

## 阶段 2 的完成条件

CLI 统一发现题集、校验计划、调度执行、控制任务、整理证据与生成报告。
Agent 从 help/schema 开始可完成流程；取消、失败、重跑、幂等提交有稳定 JSON 与退出码。
执行器和分析器各自独立，工具版本与 benchmark 版本分别记录。
完整交付范围包含以下可验收模块，逐项验收状态在进度表记录：

- 环境预检/指纹、local/SSH 适配、资产与数据/缓存恢复、资源归属和清理。
- 三种服务入口及后端能力矩阵；HG 扩展的开放/闭环执行与官方 driver 的独立调度语义。
- compare/capacity/diagnose 的执行规则、逐请求计数与时间线、取消/drain 和原始证据。
- 压测端、Server、PD/Store、主机指标采集，以及指标缺失与采集成本说明。
- 正确性、完整性、可比性质量门，配对统计、效应区间、误报控制和明确的结论状态。
- 可从证据重建的交互离线 HTML/JSON 报告，环境差异、逐题结果、容量曲线和资源信息。
- Agent 友好的发现/帮助/schema/JSON、统一任务生命周期、幂等提交与恢复。

完整 LDBC track 的适配和符合性验证属于该 track 的发布条件；通用工具组件可以在文件协议和受控自动测试上独立开发。

原型中的 fixture 只证明编排行为。HTTP Serving v0.1 使用独立版本的脚本题集和真实 HTTP 组件验证执行、计数和报告；其正式性能结论仍需通过测量校准，SF100 验收单独保留。

## 阶段 3 的完成条件

在冻结的基准与工具版本下完成 issue 中的 HTTP 对比，检查语义、环境与协议条件是否可比，
报告逐题指标、误差、正确性和证据。结果用于验证工具实用性及优化假设，不反向按结果调整题集。

## 阶段 4 与扩展

阶段 4 交付固定 runner、历史索引、保留策略、nightly/weekly、确认流程与成熟案例门禁。
JMH/引擎层统一适配、FinBench、Graphalytics、运行维护/故障、多压测机和跨数据库比较按原设计分别扩展，逐项验收。
这些能力没有取消，也不以“SF100 接入完成”自动计为完成。
