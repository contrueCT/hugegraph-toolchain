# 当前开发顺序：HTTP 工具闭环优先

2026-10-22 用户调整优先级：先让评测工具在不需要大图的场景下完整运行，再用 HTTP 转发消除做实测；暂时跳过 SF100。

这是当前开发顺序。原有阶段编号继续表示验收归属，SF100 阶段仍未完成；其后续导入、参考答案、HStore 校准和独立复现在本专项之后接回。

## 主线目标

交付一套系统、可复用、方便人工与 agent 使用的 HG-Bench 测评工具。以不依赖大图的 HTTP Serving 基准完成规范、执行、校准、比较、报告和复现的整个闭环，再把 HTTP 转发消除作为首个实际优化评估案例。HTTP 专项的工具能力应能复用于后续版本、配置及 SF100/HStore 测试。

架构继续采用 TypeScript 薄 CLI 加独立执行、校验、采集、分析和报告组件。当前 Node HTTP runner 的正式适用负载范围通过校准确定；需要替换执行器时沿用组件协议及计时语义。CLI 语言不约束执行器语言。

## 当前里程碑与退出条件

以下顺序控制近期开发；表中条件是待逐项核对的验收要求，不表示已经实现。

| 里程碑 | 交付内容 | 退出条件 |
| --- | --- | --- |
| M0 HTTP 基准规范与题集 | 版本化题目、参数/答案、profile、计时口径、负载模型、指标与质量/比较规则 | 明确每个场景测什么、如何复现和怎样判定；固定正式实验参数，记录校准依据 |
| M1 工具端到端闭环 | CLI 计划、真实服务预检、runner、校验、采集、证据封存、JSON/离线 HTML | 统一入口可在真实 HugeGraph 执行；失败可追踪；报告由原始证据独立重建；有可复跑示例 |
| M2 可信 A/B 执行与判定 | 受控配置切换、预热与测量窗口、重复配对、校准、可比性及效应分析 | 工具校准与目标环境检查通过；能自动完成一组真实配对，给出区间和有效性状态 |
| M3 转发消除实测 | 同一候选构建的 forward/embedded 比较 | 按预定题集输出性能变化、退化或不确定项、环境限制和完整证据；重点解释大响应的尾延迟 |
| M4 接回大图 | SF100/HStore 的数据、参考答案、正确性和性能验收 | 复用前述工具能力，并完成大图自身尚未完成的验收条件 |

### M0：固定“测什么”和“如何解释”

首版题集覆盖真实 `/gremlin` 的短脚本、结构化响应及多个响应规模，答案能够独立预先确定。单值字符串和多行结果的形态分别记录。每题固定请求、参数、答案语义及返回大小口径；后续增加固定小图点查/遍历时使用新的题集版本。

profile 明确协议、连接复用、压缩、鉴权、线程/队列、预热、采样时长、重复轮数、超时/排空、负载点和资源预算。匿名、鉴权及不同压缩配置分开报告。选定主指标和最小有意义差异，避免测量后挑选有利指标；正式参数的定值由校准支持。

### M1：由工具完成真实实验流程

```text
发现题集/能力 → 校验并冻结计划 → 核对构建和实际配置 → 健康/答案预检
       → 准备环境 → 预热 → 测量与采集 → 排空/后检
       → 封存证据 → 独立分析 → JSON/离线 HTML → 复现
```

每步定义输入、输出、超时、失败状态和资源归属。复用现有 task 生命周期；同一请求的幂等查询、断线后查状态、取消、部分证据和新 attempt 规则必须贯通。当前交付只需支持本专项的受控部署/切换步骤，通用部署平台和完整 DAG 可以后续扩展。

CLI 提供清晰 help、schema、JSON、退出码、dry-run、预算和下一步命令。自定义工作负载通过组件协议接入；所有正式产物都能追溯到冻结计划、源码/构建、环境和执行身份。

### M2：把实验策略落成可执行流程

负载包含固定并发与固定到达率。记录计划到达、提交、完整响应及排空时间；迟到、超时、错误和丢弃保留，计数可核对。校验、解压与日志写入的成本需要观测和校准。采集驱动与目标端的 CPU、内存和 JVM/GC 等可用指标，注明缺失项、时间窗口和采集开销。

A/B 使用同一候选构建、同一题集和相同外围配置，只改变声明的变量。控制器负责切换、启停、健康检查和实际模式核验；目标模式标签不足以证明模式已经生效。重复运行采用平衡顺序或固定种子的随机配对，保留实际顺序。固定时长预热须有稳定性依据；缓存与数据重置协议按 workload 明确。

先完成计时/计数故障校准、A/A 噪声检查、已知延迟/退化检出、驱动余量和采集成本验证。质量门依次检查正确性、证据完整性、测量条件和可比性；采用独立重复运行作为统计单位，给出绝对/相对效应与区间，并处理多场景比较。结论可为改善、退化、权衡、不确定或无效，不能由单轮百分位直接得出。

首版比较可以报告预先指定负载点的延迟、正确完成吞吐和资源成本；容量上限的宣称需要额外的饱和与独立确认依据。

### M3：用转发消除验收工具

本次案例通过 HG-Bench 的公开流程运行。先比较相同到达率下的响应、错误和资源成本，再观察增加负载后的变化；完整报告每个预定场景。已有人工 RocksDB 短测只用于定位问题，特别是大响应高并发下的 P99，不替代本次工具生成的新证据。

最终交付包括：HTTP 基准规范与题集、实际可用的 CLI/组件、校准证据、forward/embedded 原始与分析结果、交互离线报告、复现命令和扩展示例。每轮进度汇报对应 M0–M3 的已验证项、剩余项和下一步，模块扩展按对这些验收条件的必要性排序。

## SF100 的后续位置

当前开发主线暂时跳过 SF100，不为本次 HTTP 实测追加大图下载、转换、导入或参考库建设。已取得的规范、资产和证据保留，后续继续采用正式 SF100 规模。

本次调整只修改开发计划；既有远端任务的停止、续接与清理由原执行任务管理，不通过这份计划重启或重复提交。
